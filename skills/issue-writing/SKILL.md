# Issue Writing

経緯を知らない人が、作業の必要性と完了条件を判断できるIssueを書く。

## 執筆前に読むもの

1. [structured-writing](../structured-writing/SKILL.md)を読み、文章の共通原則を適用する。
2. 対象リポジトリの作成ガイドと、今回使うIssueテンプレートを読む。見出し・順序・必須欄・任意欄はテンプレートを正本とする。テンプレートがない場合は、リポジトリの規約と依頼の形式に従う。
3. 仮説や事前の検証計画を扱うときは、[hypothesis-and-evidence](../hypothesis-and-evidence/SKILL.md)を読む。検証の強さと完了判断は、対象リポジトリの検証ルールに従う。

このスキルは文章の作成と確認を扱う。公開・ラベル・状態変更などの操作は、依頼の範囲とリポジトリの運用手順に従う。

## 本文の組み立て

次の情報を、テンプレートの対応する欄へ配置する。

| 情報の役割 | 書く内容 |
| --- | --- |
| 背景 | 対象の機能、利用場面、関連技術、検討中の案。既存の動作と提案を区別する |
| 課題 | 期待する状態と現在の状態の違い、それで困る人と不都合。調査では、未確認点と判断できないことを示す |
| 目的 | 利用者や開発者ができるようになること、可能になる判断 |
| 完了条件 | 作業が終わったと判断できる動作や成果 |
| 検証方法 | 完了条件を確かめる操作・テスト・測定と、判定の根拠 |

タイトルには対象と、具体的な課題または実現したい結果を示す。
コメントでは、そのコメントが扱う判断・質問・報告に必要な情報だけを書く。本文用の見出し一式は、本文を作成・更新するときに使う。

## 完了条件

- 分かりやすい言葉で、操作と結果、または成果物と判断できる内容を書く。チェックリストは独立して判定できる単位に分ける。
- 調査では、どんな比較結果や判断材料が揃えば完了するかを示す。
- 判定に必要な形式・数値・用語は本文に残し、読み手が知らない用語は何を指すか説明する。
- 検証記録のファイル形式や技術的な記録項目は、検証方法の詳細に置く。

## 検証計画と補足

- 作成時に、完了条件をどう確かめるかを短く示す。共通する開始条件や環境は一度だけ書き、適用する完了条件を示す。
- 条件ごとの操作・測定、観察できる期待結果、合否基準、残す証拠、その確認では分からないことを対応づける。共通情報は参照で示す。
- 詳しい手順や記録項目は、必要な場合だけ折りたたみや資料にまとめる。
- 検討記録は本文または既存記録への参照で残す。本文を補う経緯がある場合だけ、該当する欄に折りたたみを追加する。
- 実装案は、考えられる方法と理由を示し、確定事項と提案を区別する。対象外には、今回の範囲と誤解されそうな関連作業を書く。関連Issueや資料には、親子関係・依存関係・根拠などの関係を添える。

## 書き換え後の確認

既存の受け入れ条件、チェック状態、測定値、制限、参照先を保つ。経緯や評価が変わった場合は、以前の判断と現在の判断、変更理由を区別する。
本文だけで対象・課題・必要性を説明でき、完了条件と検証方法を対応づけられることを確認する。

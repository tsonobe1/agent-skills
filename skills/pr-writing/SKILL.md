# PR Writing

経緯を知らない人が、解決する課題、変更後の結果、その根拠を判断できるPRを書く。

## 執筆前に読むもの

1. [structured-writing](../structured-writing/SKILL.md)を読み、文章の共通原則を適用する。
2. 対象リポジトリの作成ガイドと、今回使うPRテンプレートを読む。見出し・順序・必須欄・任意欄はテンプレートを正本とする。テンプレートがない場合は、リポジトリの規約と依頼の形式に従う。
3. 対応するIssue・合意した仕様、実際の差分、検証記録を照合する。検証の強さと完了判断は、対象リポジトリの検証ルールに従う。

このスキルは文章の作成と確認を扱う。投稿・コードレビュー・Issueとの紐付け操作・マージは、依頼の範囲とリポジトリの運用手順に従う。

## 本文の組み立て

次の情報を、テンプレートの対応する欄へ配置する。

| 情報の役割 | 書く内容 |
| --- | --- |
| 背景・課題・目的 | 何の機能か、何が問題だったか、変更で実現したい価値 |
| 変更後の動作 | 操作する人・機能・プログラムと、その操作で得られる結果 |
| 変更内容 | 実際の実装上の変更と、レビューに必要な理由 |
| 検証 | 実施した確認、結果、根拠、失敗・制限・未確認事項 |

- タイトルは、具体的な問題や変更後の結果が分かる表現にする。
- 本体の機能と独立した比較・検証プログラムを扱う場合は、用途と本体への組込みの有無を冒頭で示す。
- 仕様を変更した場合は、変更前後と理由、今回の範囲か後続作業かを、変更後の動作の説明に添える。実装方法を変えた理由は、変更内容へ置く。
- 権限・IPC・ネイティブ連携は、変更がある場合に変更内容へまとめる。
- 該当する作業がある場合だけ対象外を説明する。任意欄の追加・省略はテンプレートに従う。
- 再現手順・証拠・実験の経緯は、該当欄の詳細または資料から参照する。VM停止や共有枠解放などの作業終了記録は、ユーザーへの作業報告へ置く。

コメントでは、対象の指摘・判断・確認結果に必要な情報だけを書く。本文用の見出し一式は、本文を作成・更新するときに使う。

## 画像

- 変更内容の近くに、条件を揃えた変更前後の画像やGIFを置く。テンプレートの掲載位置に従う。
- 「ホスト上の実行画面」「VM内の実行画面」「オフスクリーン描画」「モック」を区別する。種別と実行・生成環境は「オフスクリーン描画 / VM」のような小見出しで示す。
- テーマ・ウィンドウサイズ・表示データなどの詳しい条件は、画像の近くの折りたたみに短いラベルで記載し、句点を付けない。

## テスト・ビルド・画面確認

テスト、ビルド、画面確認の結果を、テンプレートの対応する欄へ分けて置く。

### テスト

- 実行した場合は、実行日を該当欄の先頭に「YYYY/MM/DD 実行」の単独ラベルで示し、句点を付けない。
- 何を確かめたかと結果を短く示す。失敗・スキップ・未実施には、その内容と理由を添える。不要なら理由を書く。
- 実行結果から取得したテストケース名を、コードと対応する表記のまま全件残す。所属スイート、実際の引数、各ケースの結果を添える。
- 実際の種類に応じて、単体・結合・UI・E2Eなどに分ける。複数の種類に該当する同じ実行は一度だけ載せる。
- ケース一覧、実行コマンド・条件、ログへの参照は種類ごとの折りたたみにまとめる。ケース名の言い換えや代表例への省略は行わない。

### ビルド

対象・構成・結果を短く示す。実行コマンドは詳細または実行記録から参照する。未実施・不要なら理由を書く。

### 画面確認

実際に行った操作と観察した結果を示す。未確認の項目には、理由と確認する操作・期待結果を添える。既存の確認手順があれば参照する。

## 書き換え後の確認

Issueとの対応、実際の差分、実行した確認と結果が一致していることを確かめる。既存の検証記録、制限、測定値、参照先を保ち、以前の結果と今回の結果を区別する。
本文だけで必要性と変更後の結果を説明でき、根拠が裏付ける範囲と未確認の範囲を判別できることを確認する。
